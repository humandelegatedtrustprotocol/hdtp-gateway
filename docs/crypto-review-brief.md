# Cryptographic review brief

This document exists to make an independent review of pact-gateway's envelope
cryptography cheap and pointed. It states the construction exactly, says what is
already tested, and — most usefully — lists the questions we actually want
answered, including the ones we suspect are problems.

Nothing here has been reviewed by anyone outside the project. That is the gap this
document is meant to close, not one it closes by itself.

## The construction

**Identity.** A caller *is* a fingerprint: `"sha256:" + base64url(SHA-256(SPKI))`
over the DER SubjectPublicKeyInfo. Two algorithms: ECDSA P-256 and Ed25519.

**Sealed envelope** (SPEC §4, §13). Four base64url wire members:

```
protected   canonical-JSON header bytes  (also the HPKE AAD)
enc         HPKE encapsulated key
ct          HPKE ciphertext
sig         detached signature over protected ‖ enc ‖ ct
```

**Suites**, chosen by the recipient key type:

| Suite | KEM | KDF | AEAD |
|---|---|---|---|
| `PACT-SEAL-P256` | DHKEM(P-256, HKDF-SHA256) | HKDF-SHA256 | AES-128-GCM |
| `PACT-SEAL-X25519` | DHKEM(X25519, HKDF-SHA256) | HKDF-SHA256 | ChaCha20-Poly1305 |

HPKE **Base mode**, `info = "PACT-SEAL-v1"`, AAD = the raw `protected` bytes.
Signatures: ECDSA is ASN.1 DER over SHA-256; Ed25519 is pure RFC 8032.

**Key conversion.** An Ed25519 identity is converted to X25519 for the KEM —
RFC 7748 §4.1 for the public half, RFC 8032 §5.1.5 for the private scalar.

**Open order** (SPEC §4.4, `internal/public/identify.go`), which is load-bearing
and deliberately not the obvious order: decode → suite → addressing (`to`) → `kid`
→ **HPKE open** → **verify signature** → unified identity rule → freshness →
replay. Decryption precedes signature verification because HPKE Base needs no
sender key, and because an unpinned sender's key rides *inside* the ciphertext
(`spk`) so that carriers see only fingerprints.

## Questions we want answered

Ordered by how much we suspect them.

**Q1 — Key reuse across four roles.** One keypair is simultaneously the TLS
client certificate key, the TLS server key (direct mode, self-signed), the HPKE
recipient key, and the envelope signing key. For P-256 that is ECDSA signing plus
DHKEM(P-256) on the same key; for Ed25519 it is EdDSA signing plus X25519 ECDH on
the same scalar. This is documented and accepted (SPEC §2, §13), and the
envelope's `kid` field is the reserved seam for separating them. **Is the reuse
exploitable, or only inelegant?** If it is exploitable, we would rather learn it
before v1.0, when the wire format can still change cheaply.

**Q2 — Signature input is plain concatenation.** `sigInput` is
`protected ‖ enc ‖ ct` with no length prefixes and no domain separation tag. Our
reasoning that this is unambiguous is: `enc` has fixed length per suite, and by
the time the signature is checked the AEAD has already succeeded with `protected`
as AAD, so all three fields are pinned. **Is that reasoning complete?** We would
prefer to be told to add length prefixes than to be right by accident.

**Q3 — Decrypt-before-verify.** The order above opens the HPKE ciphertext before
any signature is checked, so unauthenticated attacker-chosen ciphertext reaches
the AEAD. HPKE Base + AEAD should make this safe, and the payload parser is
fuzzed. **Does anything about this ordering leak, or create an oracle?**

**Q4 — The blocked-sender path.** A blocked contact is deliberately handled
byte-identically to a stranger, so that acceptance cannot distinguish "blocked"
from "never met". **Is that indistinguishability real, including in timing?**

**Q5 — Replay and freshness.** Idempotency is per-`(caller, msg_id)`; direct
delivery additionally enforces a 300-second timestamp window, relaxed for relayed
delivery because a store-and-forward hop may be arbitrarily late. **Is the relaxed
window exploitable given the idempotency store, and is 30 days a defensible
lifetime cap?**

**Q6 — Ed25519 → X25519 conversion.** Standard, but conversion plus signing on the
same key is exactly the combination the literature warns about. **Is our use
within what is considered safe?**

## What is already checked, so you need not

- **Test vectors**: `internal/envelope/testdata/vectors.json`, regenerated by
  `internal/envelope/cmd/genvectors`. `TestVectorsOpenAndVerify` and
  `TestVectorsDeterministic` run them; they are the interop artifact for a second
  implementation, of which there is currently none.
- **AAD binding**: `TestAADTamperFails`.
- **Forgery**: `TestPinnedSenderPathAndSPKMismatch` builds a real envelope claiming
  a contact's fingerprint while signing as somebody else.
- **Parsers**: four fuzz targets in CI, including the envelope wire format and the
  sealed payload (~7M executions at introduction, no crashes).
- **Ordering**: the numbered steps of §4.4 have individual tests.
- Full claim-to-test map in [threat-model.md](threat-model.md).

## Explicitly not asking about

These are decided, documented in SPEC §13.2, and not defects: no forward secrecy
at the envelope layer (HPKE Base to a long-lived key); metadata visible to relays
and edges; no key recovery. A review is welcome to argue the decisions were wrong
— but they were decisions.

## Reproducing

```
git clone <repo> && cd pact-gateway
make check                 # fmt, vet, race tests, both storage engines
go test ./internal/envelope/ -run TestVectors -v
```

The construction lives in `internal/envelope/envelope.go` (~280 lines) and the
identity decision in `internal/public/identify.go`. Those two files are the review.
