## R2 · An export is chats and contacts, and nothing else — `DONE`
Today the node's `backup create` is a snapshot of the whole database (every table; leaf keys
stripped since F1) with the blobs and, by default, `keyring.key`. The cloud's identity archive is 22
tables — owners, credentials, sessions, tokens, audit, invites, integrations (with the upstream
secret REVEALED), settings, the relay tables — sealed to the owner.
The rule: an export carries **the identity's name** (slug, display name, the root's fingerprint and
certificate — public, and what the data belongs to), **contacts**, and **chats** (threads, messages,
and the media they reference). No key of any kind, no settings, no credentials, no sessions or
tokens, no audit chain, no invites, no leaf ledger. Every import ends at an account that is named
and not served until its wallet issues THIS host a new leaf.
- **R2a · node.** A logical export written THROUGH the `Store` interface — so it is an allow-list by
  construction, works on Postgres as well as SQLite (a Postgres node has never had an export), and
  needs no hand-written SQL. One JSON manifest line and JSON Lines rows, in a tar with the media.
  `pact-gateway export` / `import` replace `backup create` / `restore`: it is not a backup of the
  node any more and must not be called one. **Goes:** the database snapshot, `SQLite.Snapshot`
  (E2's single counted exception — the count becomes zero), `StripKeys` and its queries,
  `-same-node`, `-data-only`, `-without-master-key`, the keyring-id manifest, and their tests.
  The lost-master-key recovery of F1b becomes: `export`, a fresh data directory, `import`, a leaf.
- **R2b · cloud.** The owner's export builds from the same allow-list; nothing is revealed, so the
  `reveal` ports, `KEY_MATERIAL_INCLUDED_NOTE` and the keys-included branch go. The platform's own
  weekly snapshot is NOT an export — it never leaves the platform — and keeps its full table list.
  `npm run leave` stops fabricating a SQLite store with goose bookkeeping ("29 versions through
  29") and writes the node's import file instead: the coupling E3/B2c kept tripping over is gone.
  `import20.ts` takes the same allow-list.
  *To establish, not assume:* the workspace document in `index.pact` is what `docs/privacy/dsar.md`
  says serves GDPR access and portability. That is a legal duty, not a product choice; it is left as
  it is unless the owner says otherwise, and that is stated in the hand-over.
- **R2c · protocol and docs.** §9 lists "contacts, messages, media, invites, settings"; it says what
  travels now. Node SPEC §3.10/§11/§12, README, operations, the cloud's export doc and terms.
*Verify:* a test that reads an export's BYTES and finds no table but the four, no key, no setting,

**Design, settled before any code (2026-09-19):**
- *Object migration `1004_drop_1x`, forward-only, one transaction per migration.* The runner was
  not transactional: a statement failing half-way left a version unrecorded and statements that
  cannot be re-run (`DROP COLUMN` of a column already gone), which bricks an object at start.
  Each migration now runs inside the object's `transactionSync`.
  Drops `accounts.protocol, accept_1x, prev_fingerprint, prev_key_sealed, grace_until` and
  `contacts.protocol`; deletes fan-out rows that are not a move's, drops `kind`, renames the table
  `move_fanout` and `new_fpr` → `leaf_kid` as the node did in 0036; drops `relay_allowlist` and
  `relay_queue`.
- *A key-pinned contact row is NOT deleted.* Its threads and messages hang off it, and deleting a
  person's data in a production object is not this migration's call. It has no leaf, and it is
  refused by what it lacks — "no certificate is held for this contact" — not by a generation
  number. `accounts.prev_key_sealed` could hold a sealed private key from a rotation in flight;
  dropping the column destroys it, which is what 1.x's own rule asked for.
- *`protocol` leaves the API as well as the schema.* On an identity it had come to mean "has the
  wallet issued a leaf yet" (1 = no, 2 = yes), a live 2.x state under a retired generation's
  number — the node's `Certified`. `/v1` answers `certified: boolean`; a certificate, an install
  and an import stop answering `protocol: 2`; a contact stops carrying it. The portal follows.
- *D1:* `identities.protocol = 2` meant "`fingerprint` is the ROOT's". The column goes; a row
  that was not 2 has its `fingerprint` set NULL first (it held a host key's, which is nobody),
  provisioning stops writing one, and `certified` is "`fingerprint` is not null".
- *Archives.* The manifest's `protocol` goes; "a 1.x export" becomes "an archive that names no
  root". A snapshot taken BEFORE this migration lists tables that no longer exist; a restore used
  to refuse any table the object lacks. It skips the three retired ones and says so in its report.
  `nodeTables()` applies the cloud migrations' DROP and RENAME, so exports and the leave file stop
  naming tables that are gone.

**Done, 2026-09-19.** Everything in the design above is built. What it touched, beyond the plan:

- *Object migration `1004_drop_1x`* and *D1 `0015_drop_1x`* (generated: the D1 manifest could
  only ADD a column; it has `removedIn`/`removedAfter` now, 0001–0014 still generate byte for
  byte, and `liveColumns` is what the data layer and the records of processing read).
- *The runner is transactional* — each migration and the row that records it land together.
  `test/migrate-1004.test.ts` rebuilds an object's storage as it stood at 1003, fills it the way
  1.x did (a rotation in flight with a sealed retiring private key, a key-pinned contact with a

  runner: the 1.x columns and the relay go, the key and the root come through, only the move's
  progress survives, the key pin keeps its messages and is refused by name when called. A
  second case makes 1004 fail half-way and shows nothing of it survives and the re-run finishes.
- *The migration lock covers object migrations now* (44 pinned, was 15). Only D1's were; an
  object records an applied migration by NUMBER, so editing a shipped one fails as silently.
- *`protocol` is gone from the API and the portal*: identities answer `certified`; certificate,
  install and import answers lost `protocol: 2`; `upgraded` is `first` and the webhook event
  `identity.upgraded` is `identity.certified`. `store.insertContact` (the key-pin writer, no
  production caller), `contacts1x`, `repinContact`, `FanoutKind` and seven relay audit
  declarations nothing could write are gone.

**What it found:**
- ***A restore rewrote who the identity was.*** A snapshot's `accounts` row carries `fingerprint`
  and `algo`, which NAME the sealed key the snapshot withholds, and `root_fingerprint`/`root_cert`.
  A restore wrote all four back. Across a renewal that left the account naming a leaf key it no
  longer held; a snapshot from before certification would have made a live identity nobody. The
  operator console then copied that leaf-key fingerprint over the ROOT in D1's routing copy
  ("reconciling across a key rotation"). `ACCOUNT_IDENTITY_COLUMNS` are never written now, the
  console reconciles nothing, and the test fails under the mutation that puts it back.
- ***Every snapshot taken before today would have become unrestorable.*** A restore refuses any
  table the object lacks, and 1004 removes three that every older snapshot lists. They are
  skipped and REPORTED (`retired`), and an unknown table is still refused.
- *The portal still offered "Rotate this key"*, with a plan, a grace window and a confirm, wired
  to `/v1/identities/:slug/rotation` — routes deleted the day before. Every click was a 404.
- *The portal's import read an empty contact book from every export since R2b*: it kept rows
  with `protocol === 2`, and an export stopped carrying that column. It keys on the leaf now.
- *`contact_accepted` stored whatever card it was sent*, unchecked, through `repinContact`
  (called with the same fingerprint twice). It is checked as `update_contact`'s is: the card's
  certificate is the leaf that signed the call, and it names the pinned root.
- *A new identity was handed a `fingerprint`* — the host key minted at creation — by
  provisioning, by `/api/workspaces/:id/identities` and into D1. A host key is nobody's identity.
- ***The deploy tooling assumed every migration adds.*** `ship-*` migrates before it deploys
  ("always migrate first"), which for a REMOVAL answers 500 on every request that names the
  column until the deploy lands; and `promote` refuses a gradual rollout only for a Durable
  Object CLASS migration, so it would have run the old version at 90% against objects the new
  one had already migrated, then rolled ALL traffic back onto it. `/healthz` reports what schema
  a build reads, `make roll` picks the order from it, `promote` refuses the ladder when the live
  version is behind, and both runbooks say so. Asked of live staging today, the answer is
  `contract`.

*Gates:* the cloud's ROOT `make check` — the gateway's 80 files and 1418 tests, ceremony

## R6 · Clearance, proven — `DONE`

dated release records). Markers, to be fixed by the diagnosis: `X-PACT-KEY|ENDPOINT|GATEWAY|SPKI`,

*Verify:* each guard fails on a planted marker and passes on the tree.

**The rule, settled by the census (2026-09-19).** Counted across every tracked file outside
append-only migrations and dated records: 70 hits in 30 files (node + identity), 92 in 34 (cloud),
16 in 4 (protocol).

- *What the guard forbids is a NAME, not a word.* A 1.x wire name, flag, mode, tool, column, table,
  audit action, event or Go/TS identifier — the things a grep is run for. They may appear in
  exactly three kinds of file: an append-only migration; a dated record (`docs/release/`,
  `docs/superpowers/`, the build logs in `PLAN.md`, the protocol's `archive/`); and a file on the
  guard's own allow-list, each with its reason — a test that feeds 1.x IN to prove it is refused,
  or a fixture of a store that lived through it. A listed file that no longer holds a marker
  fails too, so the list cannot rot.
- *A comment is not exempt.* "which is why the retired `X-PACT-KEY` is gone" keeps the name
  greppable for ever; the sentence survives without it. The generation's own name ("1.x") is
  NOT forbidden: the spec itself has to say "PACT 1.x is not supported", and a comment may say
  why code has the shape it has. What is cleared by hand, and listed below, is prose that
  describes a 1.x behaviour as something this software DOES.
- *One list, four guards.* Each repository carries its own copy, because two of them are their
  own repositories; the node's guard compares the siblings' lists with its own when they are
  checked out beside it.
