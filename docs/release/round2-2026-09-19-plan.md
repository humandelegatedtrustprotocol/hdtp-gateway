## R2 · An export is chats and contacts, and nothing else — `DONE`
Today the node's `backup create` is a snapshot of the whole database (every table; leaf keys
stripped since F1) with the blobs and, by default, `keyring.key`. The cloud's identity archive is 22
tables — owners, credentials, sessions, tokens, audit, invites, integrations (with the upstream
secret REVEALED), settings, the relay tables — sealed to the owner.
The rule: an export carries **the identity's name** (slug, display name, the root's fingerprint and
certificate — public, and what the data belongs to), **contacts**, and **chats** (threads, messages,
and the media they reference). No key of any kind, no settings, no credentials, no sessions or
tokens, no audit chain, no invites, no leaf ledger. Every import ends at an account that is named
and not served until its wallet issues THIS host a new leaf.
- **R2a · node.** A logical export written THROUGH the `Store` interface — so it is an allow-list by
  construction, works on Postgres as well as SQLite (a Postgres node has never had an export), and
  needs no hand-written SQL. One JSON manifest line and JSON Lines rows, in a tar with the media.
  `pact-gateway export` / `import` replace `backup create` / `restore`: it is not a backup of the
  node any more and must not be called one. **Goes:** the database snapshot, `SQLite.Snapshot`
  (E2's single counted exception — the count becomes zero), `StripKeys` and its queries,
  `-same-node`, `-data-only`, `-without-master-key`, the keyring-id manifest, and their tests.
  The lost-master-key recovery of F1b becomes: `export`, a fresh data directory, `import`, a leaf.
- **R2b · cloud.** The owner's export builds from the same allow-list; nothing is revealed, so the
  `reveal` ports, `KEY_MATERIAL_INCLUDED_NOTE` and the keys-included branch go. The platform's own
  weekly snapshot is NOT an export — it never leaves the platform — and keeps its full table list.
  `npm run leave` stops fabricating a SQLite store with goose bookkeeping ("29 versions through
  29") and writes the node's import file instead: the coupling E3/B2c kept tripping over is gone.
  `import20.ts` takes the same allow-list.
  *To establish, not assume:* the workspace document in `index.pact` is what `docs/privacy/dsar.md`
  says serves GDPR access and portability. That is a legal duty, not a product choice; it is left as
  it is unless the owner says otherwise, and that is stated in the hand-over.
- **R2c · protocol and docs.** §9 lists "contacts, messages, media, invites, settings"; it says what
  travels now. Node SPEC §3.10/§11/§12, README, operations, the cloud's export doc and terms.
*Verify:* a test that reads an export's BYTES and finds no table but the four, no key, no setting,
no token; a round trip node→node on both engines; cloud→node through `leave`; every gate.

**R2a — `DONE`, 2026-09-19.** `internal/portable` is the format and both directions; `export` and
`import` are the verbs; `backup` is gone, with `SQLite.Snapshot`, `StripKeys` and its two queries,

- **An allow-list by construction.** The exporter asks the `Store` for an identity's name, its
  contacts, its threads and messages, and its media, and writes what it is given: five kinds of
  JSON line. There is no column to blank and no table to drop, which is what the snapshot design
  needed and what F1 spent a day getting right. The test plants a leaf key, a ledger key, a secret
  setting, a token hash, an invite label and an integration endpoint, and searches the archive's
  BYTES for each.
- **Strict on the way in.** A member, a kind of line or a single FIELD the importer does not know is
  a refusal; so are data that does not match the manifest's digest, media that is not the file its
  name says, and a root certificate that is not the root it travels under. Each is tested, and each
  is checked to have written nothing.
- **Atomic, on both engines.** `Store.Atomically` re-points the engine's query object at one
  transaction — every store method already reaches the database through it, so nothing needed a
  second, transactional spelling — and the store's conformance suite proves rollback and
  read-your-writes on SQLite and Postgres. A Postgres node can export, which it never could.
- **Three mutants, three failures**: an exporter that also writes a setting; an importer that stops
  being strict about fields; an import with no transaction.
- An undelivered outbound message arrives as `failed` with no retry schedule. Delivering it was the
  old host's job under the old host's leaf, and the importing host must not inherit a send queue.
- **E2's guard has no exception left.** Its one counted exception was `VACUUM INTO`.
- **Found on the way.** `export` typed bare made the default data directory and migrated a store in

**What it found:**
- *A refresh over a sealed call misreported a renewal as "updated", on both hosts.* The answer's
  chain repins on the way through (§14.3), so by the time the card is read the newer leaf is
  already the pin. "Renewed" is now judged against the leaf held BEFORE the call.
  `TestRefreshingOneContactOverTheWire` failed first; the cloud's test fails the same way under
  the same mutation.
- *The cloud's `get_card` and `redeem_invite` did not answer what PACT §6.1 says they answer.*
  `{card}` and `{status, card}`, against `card`, `card_sig`, `chain` (and `limits`). The node's
  refresh needs the signature and the chain — they ARE the trust decision — so a self-hosted
  owner pressing the new button on a cloud-hosted contact would have been told an honest node
  "did not verify". The live battery had the assertion, inside the half that skips without a
  token, and it looked at the chain alone. Fixed (`signedOffer`, one function for the landing,
  `redeem_invite` and `get_card`; `limits` from the enforcing constants, the invite cap among
  them, which was a bare `90`); the battery's case now checks signature and limits too. **Unrun
  against a deployment until the next `ship-staging`.**
- *`test/fixtures/go-owner-tools.json` was a hand-copied list nobody checked.* It lacked
  `identity_certificate` and would have kept `sync_contacts` for ever, with the cloud's parity
  test green throughout. The node now reads the sibling fixture and compares it with the tools it
  registers (`TestTheCloudsCopyOfTheOwnerToolsIsCurrent`), and the cloud serves
  `pact_identity` › `certificate`, which that comparison then demanded.
- *The node's own portal-parity test read tool names with a pattern that missed two of them*
  (`wait_for_updates`, `digest`: `Name:` on its own line) and carried three entries for tools
  that do not exist (`agent`, `ask_me`, `inbox`). Syntax tree now; a stale entry fails.
- *Three stale claims:* the node's `docs/conformance.md` said "the 2.0.0-draft … Appendix C … on
  the branch `pact-2.0-node`" (none of the three exists); the cloud's listing-budget comment said
  "2663 bytes today, about 666 tokens" (2984 and 746: the budget of 750 is all but spent, and
  says so now, with a date); `PLAN.md`'s action list named `sync` and half the real actions.
- *Left for R5/R6, seen here:* the cloud's `setTrustFlag`, `renameContact` and `addContact` owner-MCP
  actions answer `unavailable` although the Identity object can do the first two; `coverage.ts`
  still has `owner.relayFetch`; `store.repinContact` is 1.x rotation with no caller checked yet;

  ever run; the campaign's own tests use SQLite. `MoveFanoutIsOneRowPerContactAndResumable` runs

  fresh `make harness-image`: `TestLiveGuestTierSurfaceOverRealMTLS` fails in 46 s). The targets
