# Outbound webhooks on the node, ported from BatonDeck — plan

Status: **approved with the rulings below** (2026-10-18).

Owner's order (2026-10-18): "we need to copy webhook functionality from batondeck". Why: the
Product Hunt launch needs a public demo node answered by an open-source agent, and the owner wants
that agent woken by a webhook rather than a long poll.

## The owner's rulings (2026-10-18)

A. **Registration is through the portal only, by the node's owner/admin.** That is the passkey
   session on the host's portal. No owner MCP tool and no CLI command registers, rotates or
   deletes a webhook, and both are on the divergence list held by W4's test. Because only the
   owner can point one, loopback, LAN and plain `http://` are **allowed**, so an agent on the same
   host or in the same compose project is a receiver. This is a named divergence from the cloud's
   `not_https`, `literal_address` and `private_name`; `not_a_url`, `has_credentials` and
   `unknown_event` stay.
B. **Full port, including the admin dashboard** (the portal's Webhooks page, the delivery log).
C. **Delivery as BatonDeck has it:** one attempt, never retried, a pause after 20 failures. The demo
   agent reconciles with `get_inbox` on start and on a timer.
D. **Method:** "we literally want to copy and then refactor the functionality in the gateway
   code so we can ship it fastest way possible". Each file of `batondeck/gateway/src/webhooks/`
   is translated to Go one for one, with the same names, constants, refusal codes and test cases.
   Then it is refactored onto the node's store, keyring, bus and portal. The cloud's tests are the
   checklist for the node's tests.

## What exists (read 2026-10-18)

- **The node has no webhooks.** No Go file under `internal/` or `cmd/` mentions one. The only hit is
  `web/src/audit_names.ts:51`, a display name the portal shares with the cloud.
  SPEC.md §8.5 says "Nothing is pushed" (of the owner MCP), and §7.8 gives the event bus two
  consumers: the portal SSE and `wait_for_updates`.
- **The node's event bus** (`internal/messaging/bus.go`) has kinds `message`, `request`, `pending`,
  `delivery`, `call`, `attention`, `answered`, `relayed`, `invalidate`, `account`. Every event is
  also a row of the store's `changes` table, kept for a week, with a store-assigned, ordered id
  (§7.8). That id is the cursor `wait_for_updates` uses.
- **BatonDeck's webhooks** (`batondeck/gateway/src/webhooks/`, README read in full):
  - HTTPS endpoints per workspace, each with an event filter (empty means all), filtered against
    `SUBSCRIBABLE_EVENTS` (the `emitted: true` names in `src/events/registry.ts`).
  - Envelope `{id, type, created_at, identity?, data}`, carrying **ids only, never content**.
  - Headers `X-BatonDeck-Signature: t=<s>,v1=<hmac>[,v1=<hmac>]` over `<t>.<body>`, plus
    `-Event-Id`, `-Event-Type` and `-Delivery`. Tolerance 300 s. Secret `whsec_` + 32 random bytes.
  - **One attempt, never retried** (owner's decision, 2026-09-10). 10 s timeout. A response excerpt
    of 500 bytes is kept in a delivery log. 20 failures in a row pause the endpoint; only the owner
    resumes it. Rotation keeps the previous secret for 24 h and signs with both while it lasts.
  - The secret is sealed at rest (AES-GCM, workspace id as additional authenticated data).
  - URL refusals: `not_a_url`, `not_https`, `has_credentials`, `literal_address`, `private_name`;
    an unknown event is `unknown_event`.
  - Doors: the portal, `/v1` and the owner MCP: list, create, rotate, pause/resume, delete,
    deliveries.

## Feasibility (house rule "Reality first" 4)

- **The existing standard:** BatonDeck's contract above. The node copies it name for name, so a
  receiver written for one works for the other, and one agent can serve both hosts.
- **The simplest option:** a dispatcher that is a third reader of the `changes` log. It keeps its
  own cursor in the store, and for each new row it posts one signed envelope to each matching
  endpoint. Waking it is the bus's job, as §7.8 already does for its other two consumers. It is
  not a queue, and a node restart loses nothing the log still holds.
- **The cheap probe, before W1 is built:** a 30-line Go test against a real SQLite store. Append a
  `message` event through `messaging.Service`, read it back from `changes` by cursor in a second
  goroutine, and POST it to an `httptest` server. That shows the log carries the ids the envelope
  needs (thread, message, sender fingerprint), **and that a `message` row tells inbound from
  outbound**; without that, `message.received` and `message.delivered` cannot be told apart. If it
  does not, W1 starts by adding them to the row.

## Placement

The node only: `hdtp-gateway`, plus its SPEC.md (the node's own spec). HDTP's wire is untouched.
`hdtp-spec/docs/specification/1.0/` does not mention `wait_for_updates`, pushing or webhooks
(grepped 2026-10-18), so `hdtp-spec` does not change. Its mentions are in `archive/`, `docs/landscape-and-roadmap.md` and SEP 0006, which
cites the cloud's `message.received`. BatonDeck is not touched, except one test that reads both
registries (W4).

## Further decisions this plan takes (the owner may overturn any of them)

1. **Copy the one-attempt rule.** The same reasoning as the cloud's. A receiver that needs certainty
   calls `wait_for_updates` or `get_inbox`. Retries are not added.
2. **URL rules:** set by ruling A above.
3. **Header names:** `X-HDTP-Signature`, `X-HDTP-Event-Id`, `X-HDTP-Event-Type`,
   `X-HDTP-Delivery`, and the user agent `hdtp-gateway-webhooks/<version>`. The grammar is the
   cloud's. Renaming the cloud's headers to `X-HDTP-*` is not part of this plan.
4. **No feature flag.** A node owner who registers no endpoint gets no traffic.
5. **Scope per identity (account).** A webhook belongs to one account on the node, as an endpoint
   belongs to a workspace in the cloud. The envelope's `identity` is the account's id
   (team-lead's correction, 2026-10-18; it first said the slug): every owner MCP tool takes
   account ids, so a slug would make a receiver search every account. The cloud's `identity` is
   the slug (`batondeck/gateway/src/identity/identity.ts`, the event handed to `enqueueEvent`), so
   this is a named divergence from the cloud, in `internal/services/webhooks/README.md`'s list and
   held by a test. (The correction's first wording said the cloud's was its identity's id; that was
   false.)

## Items

Each item: a branch, `make check` + `make analyze` + `make sqlc-check`, mutation-checked tests, a
PR, merge, then the next. W1, W2 and W3 ship as one PR (team-lead, 2026-10-18), so that every gate
is green at its one merge; a job is never left red "for now". W1 alone gives the service no caller
in the binary. With W2, the dispatcher reaches what it posts with, and `make deadcode` still found,
measured on 2026-10-18, `Refused.Error`, `Service.Create`, `Service.Remove`, `Service.seal`,
`webhooks.CheckEndpointURL`, `webhooks.CheckEvents`, `webhooks.NewSigningSecret`,
`webhooks.Subscribable`, `webhooks.noEndpoint` and `webhooks.refused` unreachable. None of them can
be excused by a row of the Reachability table: the deadcode check wants a row per function, and the
hermetic gate calls a row stale when production code names the function at all (all of these are
named by `Create` or share a name), or when it is unexported. Only W3's page calls them.

### W0 — the probe (above). Nothing is merged; the result goes in this file.

**Result (2026-10-18, run against a real SQLite store; the probe test was not kept):** the log did
**not** carry what the envelope needs.
- The `message` change rows of an inbound and an outbound message were the same row: account,
  `kind: message`, the thread, the contact's fingerprint, an empty ref, the second. There was no
  message id and no direction, so `message.received` could not be told from a message the node
  sent, and `media.received` could not be told from a text.
- A `delivery` row held the new status in its ref and no message id.
- A deleted thread publishes a `message` event naming no message.

So W1 begins by adding them. Migration 0006 gives `changes` the columns `msg_id`, `direction` and
`msg_kind`. `messaging.Service` writes all three for every message it records, and the node's
`setStatus` writes the message id of a delivery status. A deleted thread's row keeps them empty.
This is held by `TestAMessagesChangeRowNamesTheMessageItsDirectionAndItsKind` (internal/messaging)
and `TestADeliveryStatusRowNamesItsMessage` (internal/node). The cursor table `webhook_cursor` is in
the same migration, built with its only reader, W2's dispatcher, in the same PR.

### W1 — store and core (`internal/services/webhooks/`)

- Migration and `queries/webhooks.sql` (sqlc only, ASCII):
  - `webhook_endpoints` (id, account_id, url, events, status, failures, secret_sealed,
    previous_sealed, previous_until, created_at);
  - `webhook_deliveries` (id, endpoint, event_id, type, status, http_status, latency_ms, excerpt,
    created_at);
  - `webhook_cursor` (the dispatcher's position in `changes`).
- The secret is sealed with the node's keyring (`internal/core/keyring.go`, `Encrypt(plaintext,
  aad)`: AES-256-GCM under the master key, "the ONLY write path for secrets at rest"), with the
  endpoint's column and account id as additional authenticated data, as `integrations.SealOAuth`
  (`internal/integrations/oauth.go`) seals OAuth tokens. It is shown once, at create and at rotate.
- URL check and event check, with the cloud's refusal codes. Sign and verify, with the cloud's
  grammar and tolerance; the verifier is kept so tests exercise what the docs tell receivers.
- Event names: the cloud's names for what the node emits. The mapping from bus kind to name is
  written once, and W4's test holds the list.
- Refusal tests (Building rule 3): unknown endpoint 404, another account's endpoint 404, malformed
  URL/event 400, paused→rotate allowed, delete twice 404.

As built, where W1 differs from the lines above:
- The additional data is `webhook-secret:<account>:<endpoint>`, without the column. A rotation
  moves the current blob into `previous_sealed` in one statement, and it must still open there.
- `webhook_cursor` (account_id, last_change_id) is built in the same PR as its reader, W2.
- The audit rows are written in W1's service, in the node's snake_case: `webhook_create`
  (`account:<id> webhook:<id> host:<host>`), `webhook_rotate`, `webhook_pause`, `webhook_resume` and
  `webhook_delete`. The row names the host, never the URL: receivers put tokens in query strings,
  and an audit row cannot be edited afterwards (team-lead, 2026-10-18).
- The verifier (`VerifySignature`, `ParseSignatureHeader`) is in `verify_test.go`: the node never
  verifies a signature, so it is not in the binary. The dispatcher's signed-delivery test verifies
  with it what the receiver got.

### W2 — the dispatcher

- A process goroutine reads `changes` from `webhook_cursor` (one row per account, `account_id`),
  woken by the bus with the 250 ms poll as the floor. For each row: `targetsFor` (active, subscribed, created no later than the event),
  one POST per endpoint in sequence, 10 s timeout, a 500-byte excerpt, a delivery row, the failure
  count, a pause at 20. Then it advances the cursor.
- Several node processes on one PostgreSQL store (§11.1) must not deliver twice: the dispatcher
  holds a store lease (advisory lock on PostgreSQL; on SQLite the store is single-process). Tested
  with two dispatchers against one store, expecting exactly one POST.
- The node has no single outbound URL guard today. The checks are `messaging.IsPrivateAddr`
  (used at `internal/node/send.go:642`) and the LAN guard in `internal/public/lan.go`. W1 takes the
  URL check into one function. The dial re-checks the address it actually connected to, by the
  rules ruling A sets (Building rule 11).
- A failure never fails the event's cause. Logs carry a code, never error text (Building rule 10).
- An endpoint removed mid-batch receives nothing after its removal.

As built, where W2 differs from the lines above:
- The cursor is claimed for a change BEFORE the change is posted, not advanced after it: a
  compare-and-set from the id it was read at (`ClaimWebhookCursor`). A process that stops mid-post
  does not post the change again, so the delivery is at most once, as ruling C has it.
- The lease is the node's existing store lease, `webhooks`, kept by `serve`'s lease keeper with
  `retries` and `retention` (SPEC §11.1), not an advisory lock. It holds on SQLite as on
  PostgreSQL. The claim is what holds when a holder stalls past its lease. Both are held by
  `TestTwoDispatchersOnOneStorePostEachChangeOnce`, run on SQLite and on PostgreSQL.
- There is no dial re-check: ruling A allows every address, so there is nothing to re-check. A
  redirect is not followed (its 3xx is the answer, and a failure): it would post the signed event
  to an address the owner did not name.

### W3 — the portal door (ruling A) and the admin dashboard (ruling B)

- Portal: a Webhooks page per account (list, add, show the secret once, rotate, pause/resume,
  delete, the delivery log with status, latency and excerpt), behind the portal's passkey session
  and its existing owner check. It mirrors the cloud portal's webhook page.
- The page's handlers call W1's service and nothing else. The owner MCP and the CLI do not
  register webhooks (ruling A), and W4's divergence list names both doors.
- Audit (Building rule 7): `webhook_create`, `webhook_rotate`, `webhook_pause`, `webhook_resume`,
  `webhook_delete`, one row each, written by W1's service. `webhook_create` names the host, never
  the URL. Deliveries are not audited: the delivery log is their record, as in the cloud.

As built, where W3 differs from the lines above:
- The page is BatonDeck's `portal/src/views/webhooks.tsx`, copied and moved onto the node's
  components and forms (`web/src/views/webhooks.tsx`, `/webhooks` in the identity's places). The
  cloud's "not switched on" notice is gone (decision 4: no feature flag), and so is its delivery
  log's `try` column (always 1). Its routes: `GET /api/webhooks`, `GET /api/webhooks/{id}/deliveries`,
  `POST /webhooks/create`, `/webhooks/{id}/rotate`, `/webhooks/{id}/status`, `/webhooks/{id}/remove`
  (`internal/internalui/webhooks_pages.go`), each a call of the one service `serve` hands the
  dispatcher too.
- The service imports the store, `internal/messaging` (the change log and the delivery statuses)
  and `internal/refusal`, and nothing of the node. The layering table ranks it 5,
  under the portal's 6, which is its door.
- The review of 2026-10-18 added bounds and housekeeping to W1 to W3: at most 100 endpoints per
  account (the next is a `conflict`, audited as `endpoint_cap`) and a URL of at most 2,048 bytes
  (`url_too_long`), where the cloud refuses neither; an account's first endpoint starts the
  dispatcher's cursor at the newest change; a status that is neither active nor paused is audited
  (`webhook_status`); an attempt cut short by the node stopping is logged and not counted toward
  the pause.

### W4 — parity, prose, release

The review of W1 to W3 (2026-10-18) asked for the cloud parity to be held by a test (A7). That stays
here, in W4: W1 to W3 compare with the cloud by reading it, and name each divergence in
`internal/services/webhooks/README.md`.

- A test holds the node's subscribable names to the cloud's `SUBSCRIBABLE_EVENTS` (it reads
  sibling `batondeck`, as the existing parity guards do), with a named divergence list for what one
  host emits and the other does not. A second test holds the envelope and header grammar.
- SPEC.md: §7.8 gains the third consumer; §8.4/§8.5 gain the tools, and "Nothing is pushed" is
  rewritten to be true of both the MCP and the webhooks. README how-to "Wake your agent with a
  webhook", including a receiver's verifier in a few lines of JS and Go. Grep every repository for
  prose that says the node pushes nothing (Building rule 2).
- Harness: one hermetic scenario. A contact messages the node, and a receiver in the harness gets a
  signed `message.received` it verifies.
- CHANGELOG, then release v0.3.0 (with the ghcr image, a separate checklist item).

## Rules walked (Building 1, 3, 4, 5, 7)

- **1, one implementation:** one service, and the portal is its only door (ruling A). W4 names
  the owner MCP and the CLI in the divergence list, and compares with the cloud by test.
- **3, refusals:** in W1.
- **4, one choke point:** the portal's existing passkey session and owner check.
- **5, both ends:** each subscribable name has an emitter (the bus kind), held by W4's test. No name
  is offered that the node does not emit.
- **7, audit:** in W3.
- **8, ways out:** a paused endpoint has resume; the previous secret stops being accepted at 24 h,
  and the hourly retention pass clears it at rest after that; delivery rows expire at the cloud's
  30 days, deleted by the same pass (`retention.WebhookDeliveriesKept`).

## What it will not do

Retries, backoff, dead letters, content in payloads, automatic resume. All of these are as the
cloud has them. (As built, W2: no address is checked at delivery, by ruling A; a name is resolved
when the HTTP client opens a connection.)
