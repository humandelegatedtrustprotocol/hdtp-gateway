# PR #29 (the one-way vault in pact-identity and the node): the review's findings, and the fix round

The code review of umbrella PR #29 (branch `feat/vault-one-way`, 2026-09-26) ran as finders, then
one verifier per candidate, then a sweep for gaps; its orchestrator stopped at the usage limit before
it reported, and this plan is assembled from its verdict tally (every row below was confirmed by a
verifier or measured; C15 was refuted and is dropped). Severity 4 is an identity-safety defect, 1 a
cleanup.

## Decided by the owner, 2026-09-26

- **D1: the SPEC allows a passphrase.** The CLI keeps the typed passphrase; §9 says a wallet
  without a credential seals the file under a passphrase the person chooses, and the recovery key
  is the form it takes in a wallet that generates one. (pact-protocol PR #3.)
- **D2: issue as a replacement.** With no record beside the vault (after the path is resolved), an
  issuance is a move: the new leaf replaces whatever was live, and the CLI says so before it signs
  and in what it prints. A typo'd `--vault` is refused as absent (C2), so the replacement is reached
  only with a real vault.

## The two questions (as put to the owner)

- **D1 · the CLI's key (S3).** SPEC §9 says the file is sealed under "a recovery key generated by
  the wallet, shown once, offered as a file", and §2.1 sends the CLI to §9. The `pact` CLI asks the
  person to TYPE a passphrase twice; nothing is generated or offered. musts.json marks the sentence
  held by CLI tests that never exercise it. Either the CLI generates the recovery key as the wallet
  page does, or §9 names the passphrase as the CLI's form of it.
- **D2 · a vault whose record cannot be found (C21, S2).** The CLI finds the record by string
  surgery on the `--vault` argument, and when nothing is there it starts an empty record. A vault
  copied alone, or reached through a symlink, then issues a SECOND live leaf for a new endpoint
  with no `--move` (measured; before this PR the ledger travelled in the vault and the same
  sequence was refused). The path is resolved either way (S2); the decision is what happens when the
  record is really gone: refuse to issue until it is restored, or issue only as a replacement.

## Items, in landing order

### P1 · the CLI's two files (pact-identity/crates/pact)
- C21 + S2 (sev 4): resolve the vault's real path before deriving the record's; then D2.
- C3 (sev 4): `id backup --force --to <the record's own path>` replaces the live record with the
  vault's bytes and reports success. A backup refuses any destination that is either source.
- C1 + C2 (sev 3): `id ledger`, `contacts export|import` never open the vault: an absent record is
  sealed under an unverified passphrase, and a typo'd `--vault` answers `[]` with exit 0. Every
  record command opens the vault first (the passphrase is proved), and an absent vault is refused.
- C4 + C5 (sev 3): backup and restore of two files are not atomic; a failed half leaves the other,
  the message says "run again" and the rerun is refused. Both land to temporaries, prove both, then
  rename both; on failure nothing is left.
- S1 (sev 2): `id create` writes the vault, then the record; a failed record write leaves a made
  identity. Same shape: both, or neither.
- C12 (sev 3): `card attach` rewrites the vault, against "written once, and again only when
  re-bound" in six places and SPEC 9.#6. Either the holder moves into the record, or the prose
  names the card as the third writing. (Decided in the item by what the card needs at open.)
- C7 (sev 2): a record without `ledger` is read as empty, a leaf is signed, then the write refuses.
  Refuse before signing, naming the file.
- C17, C19, K1–K4 (sev 1): the un-wiped plaintext on the early return; the two stale doc comments
  (card_holder, vault.rs module); four Argon2 runs where two do; one prove helper; the dedup.

### P2 · the core, both ports, the contract (one change, then the pin)
- C6 (sev 3): an unparseable ledger or date reads as no ledger, so one-live-leaf fails OPEN; Go
  refuses type mismatches but also fails open on dates. Both ports refuse.
- C8, C9, C10, C11 (sev 2–3): the ports disagree on refusal order, code and words for wallet_issue
  and vault_seal, and Go leaks encoding/json wording. One order, one vocabulary; parity cases for an
  earlier-generation document, a non-JSON plaintext, a non-object record and an out-of-range KDF,
  each red first.
- C18 (sev 2): the contract claims `pkcs8 | holder` are exclusive, `v` is 2 and no other member is
  allowed; neither port enforces it. The ports enforce what the contract says (or the contract says
  what they enforce), and the validator runs where the case is.
- C20 (latent): Go's VaultRoot/VaultContact lack members Rust writes; add them and hold the two
  structs to the contract.
- Then: `sh gate.sh`, commit, `sh js/reproduce.sh --pin`, commit the manifest, re-vendor into
  pact-cloud, `check-wasm`, `build-ceremony --pin`, the cloud gate.
