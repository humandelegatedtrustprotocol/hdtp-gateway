# services/settings

The owner-set configuration layer (SPEC §8.2, §12.2): settings rows are read from the store at startup, layered under the environment, and written back by the portal. A save either takes effect in the running node or is marked restart-scoped. `internal/cli/serve.go` builds the `Service` and calls `Values`, `Overlay`, `Follow` and `Deps`; `internal/cli/serve_admin.go` also uses it, and `doctor.go` builds one with no keyring for `Overlay` and calls `ServedIdentities`; `internal/services/retention` reads its windows through `RequestExpiryFor` and `StorageFor`. It calls `internal/node`, `internal/messaging` (the event bus), `internal/contacts` (presets, default expiry), `internal/identity`, `internal/ingress`, `internal/tunnel`, `internal/internalui` (the page's dependency struct) and the store.

## What it holds

- `Service` (`New(st, kr, cfg, audit)`): `AttachNode`, `AttachBus`, `SealPolicy`, `Follow`, `Values`, `Overlay`, `Deps`, `ContactCap`, `RequestExpiryFor`, `StorageFor`.
  - `Values` returns every stored setting with secrets decrypted; it is the startup path and the only decrypting read. The render path (`ownerValues`, also the settings page's `Pending`) reads only the keys `core.OwnerSettableKeys` names, dotted ones (`limit.contacts`) included, and never a secret row.
  - `Overlay` layers the owner-settable knobs the store holds under the environment and the file (`core.Config.ApplyStoreSettings`). It reads through `ownerValues`, which is enough because no such knob is a secret row (`TestNoOwnerSettableKnobIsASecretRow`), so `doctor` runs it without a keyring and reads the public URL `serve` serves.
  - `save` takes the values of one save (`internalui.SettingValue`; the settings page's form, or one adapter setting) and validates every one with `core.ValidateSetting` before it writes any, seals each value when `isSecretKey` says so (the last dotted segment, lower-cased, contains `token`, `key`, `secret`, `password`, `auth`, `credential`, `passwd`, `apikey` or `pat`), stores them all in one transaction (`store.Atomically`), and then, after the commit, applies every one and publishes a settings event on the bus for each, whatever applying it or another did, so every other process takes each stored key through `Follow`. Applying is outside the transaction: when some fail, `save` answers `*internalui.NotAppliedError` naming them (their failures joined with `errors.Join`) with every row stored, and this process has applied those knobs in part or not at all until its next start; a failed write answers the store's error itself, with nothing stored.
  - `apply` pushes into the running node only `limit.contacts`, `seal`, `lan_connections` and `public_url` (`apply`); every other knob waits for a restart. With no node attached, a save is stored only.
  - `Follow` applies, until `ctx` ends, the settings other processes on the store saved (events with `Local` false), as the saving process applied them, without re-auditing and without re-sealing accounts.
  - `Deps` builds `internalui.SettingsDeps`: effective settings, save, adapter settings (names and set-ness of `tunnel.*` rows, never values), pairing and unpairing, per-account storage rows, presets (`savePreset` seeds every resolved bundle on first write; `deletePreset` of the last row restores defaults), and the reachability probe.
- Per-account keys: `StorageKeyQuota` (`storage.quota.<id>`), `StorageKeyRetention` (`storage.retention.<id>`), `ContactsKeyRequestExpiry` (`contacts.request_expiry.<id>`), and `AccountKeys(accountID)`, the list of all three, which `identity.Manager.Leave` erases.
- `MaxRetentionDays` = 36500. `RequestExpiryFor` reads the owner's days when 1 to `internalui.MaxRequestExpiryDays` (365), else `contacts.DefaultRequestExpiry` (30 days). `StorageFor` returns quota bytes and a retention window; zero is default quota and unlimited retention.
- Ingress pairing (`ingresspair.go`): `pair` runs the one-time-token exchange with `ingress.Pair`, stores the result as `tunnel.<adapter>.*` rows (`storePairing`, over `pairingKeys`, `ingress_fpr` among them and `subdomain` last), then selects the adapter and sets `public_url`, all in one transaction (`store.Atomically`); `unpair` deletes the same rows, in one transaction too; `PinnedIngress(adapter, stored)` returns the ingress fingerprint only for `ingress-terminate`.
- `LeafAddress(ctx, st, accountID)`: the endpoint of the account's current leaf, or empty. `ServedIdentities(publicURL, accts)`: for each account with a root, its root fingerprint and the endpoint a leaf must name here (used by the probe).

## What it refuses, and how

- `save`: the error from `core.ValidateSetting` for an invalid key or value, and nothing is stored; store and keyring errors pass through, and the transaction stores none of the values (`TestASaveStoresEveryKnobOrNone`); a failure applying a stored value is `*internalui.NotAppliedError`, the others applied and every key announced (`TestAKnobThatCannotBeAppliedLeavesTheOthersApplied`).
- `Values`: `settings: <key> is corrupt` for a sealed row that is not valid base64; for a row that cannot be opened with the keyring, `settings: <key> cannot be opened with this keyring` when the key is top-level (seal policy, certificates and reachability must not start under an unknown posture), but a dotted key is audited `settings_unreadable ... skipped` and left out so the node can start (`Values`).
- `pair`: `the node is not serving yet` with no node attached; `create an account before pairing` when the node holds none (a failure reading the accounts is returned as it is); `unknown account`; `this node has several identities — choose which one to pair` when none is named and there are several; a failed `ingress.Pair` is audited `ingress_pair ... refused`, nothing is stored, and `pairRefusal` answers it by what the ingress answered (`ingress.PairError`'s JSON code): `invite_invalid` is `the pairing token is unknown, used or expired`, `conflict` is `that subdomain is paired to another node` (a `refusal.Conflict`), `identity_required` is `the ingress did not accept this node's certificate`, `bad_request` is `the ingress refused the subdomain or the mode: …`, `unavailable` is `the ingress could not record the pairing; try again with a new token` (a `refusal.Unavailable`), and any other answer, a non-200 whose body holds no code of these (an ingress that answers in plain text included), is `the pairing URL answered HTTP <n> without a code this node reads`; a served certificate other than the pinned one (`ingress.ErrIngressPin`) is `the ingress served a certificate whose fingerprint is not the one given`, and anything else `the ingress could not be reached` (a `refusal.Unavailable`). The ingress's answer and the dial's error are behind the sentence, never shown. `the node is not serving yet` is a `refusal.Conflict`, `unknown account` a `refusal.NotFound`, and each other sentence a `refusal.BadRequest`.
- `unpair`: `"<x>" is not an ingress adapter` (`refusal.BadRequest`); and refuses, as a `refusal.Conflict` (`<x> is the selected tunnel — …`), while that adapter is the running or the stored `tunnel` selection; a failure reading the stored selection is returned as it is, and nothing is deleted.
- `SaveStorage`: `unknown account` for an id the store does not have; otherwise it writes the quota, retention and request-expiry rows in one transaction (`store.Atomically`), so a failed write stores none of them (`TestAStorageSaveStoresEveryRowOrNone`).

## Invariants

- A secret goes in and never comes back out through rendering: the page reads only non-secret top-level rows and, for adapters, names plus `Set` flags. Credentials are sealed with the node keyring under `core.SettingsAAD()` before they touch the database.
- `pairedAdapters` treats a stored non-empty `subdomain` as the marker that an ingress adapter is paired. `storePairing` writes the adapter's rows (`pairingKeys`), the `tunnel` selection and `public_url` in one `store.Atomically` transaction, so a write that fails on any row leaves every row as it was, a previous pairing included (`TestAPairingThatFailsOnAnyWriteLeavesEveryRowAsItWas`); `public_url` is validated before the transaction and applied to the running node after it commits.
- A changed `public_url` moves nothing by itself: accounts keep answering at the endpoint their leaf names; for each account whose leaf was certified for the node's old derived address, an `account_move_needed` audit row names the move (`apply`, the `public_url` case).
- `AccountKeys` names every per-account key function in the package.

## Held by

- `accountkeys_test.go`, `TestAccountKeysNamesEveryPerAccountKey`: parses the package's non-test sources for functions taking one `accountID string` and returning one string, requires at least three, and checks each key is in `AccountKeys`.
- `secretkey_test.go`, `TestUppercaseCredentialsAreSealedAtRest`: saves four `integration.<slug>.env.<UPPERCASE>` credentials and asserts each stored row is marked secret and does not contain the plaintext.
- `shared_test.go`, `TestASettingSavedOnOneProcessIsAppliedByAnother`: two processes on one store; `seal`, `lan_connections` and `public_url` saved on one are applied on the other, which writes no audit row.
- `apply_test.go`, `TestAKnobThatCannotBeAppliedLeavesTheOthersApplied`: through `POST /settings` on the real `Deps`, a `seal` whose apply fails (the accounts cannot be read) beside `limit.contacts`: both stored, `limit.contacts` applied here and by a second process, both announced on the bus, the notice `Saved seal, limit.contacts; could not apply seal: …`, and the audit `settings_save … ok` beside `settings_apply keys:seal error`.
- `ingresspair_test.go`, `TestAStorageSaveStoresEveryRowOrNone`: a storage save whose write fails at each of its three rows leaves all three as seeded; the control stores all three.
- `presets_test.go`, `TestPresetEditingSeedsAndRestores`: the first preset write seeds the other bundles; a deleted last row restores defaults.

No test in the package covers `pair`'s exchange (`internal/cli`'s `TestIngressPairingFromThePortal` does), `RequestExpiryFor`/`StorageFor` bounds, the `Values` corrupt/unreadable paths or `ServedIdentities`; do not cite these as held.

## What it does not do

It does not apply restart-scoped knobs live, does not render or return a secret, and does not validate adapter settings by the owner-knob rules: `POST /settings/adapter` saves through `save`, whose `core.ValidateSetting` has no rule for a `tunnel.*` or `integration.*` key and passes it (the adapter owns its shape). A `public_url` change does not announce anything to contacts.
