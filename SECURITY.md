# Security policy

If you find a vulnerability in hdtp-gateway, report it privately.

**Do not open a public issue for security reports.**

Email security@hdtp.io with the subject `[hdtp-gateway security]`, and include a reproduction
if you can. GitHub's private vulnerability reporting is enabled on this repository
(<https://github.com/humandelegatedtrustprotocol/hdtp-gateway/security/advisories/new>) and reaches
the same people, if you would rather not use email.

The policy is the protocol's:
[hdtp-spec's SECURITY.md](https://github.com/humandelegatedtrustprotocol/hdtp-spec/blob/main/SECURITY.md).
It says that reports about the implementations go to this address, and it carries the
acknowledgment and status-update commitments and the terms of disclosure. This file adds none of
its own.

## Current hardening status

Stated plainly, so that nobody has to infer it from the test count: **hdtp-gateway has not been
security-reviewed by anyone outside the project.** The one review on record
([`PLAN.md`](PLAN.md), "Code and security review, 2026-08-26") was the project's own. Run it
accordingly.

Each row says where the code stands on the day it was measured, 2026-10-10, against the tree this
section was written in and the assets of release v0.1.2, and names the file, target or test that
holds it. The rows that can be derived from the tree are held to it by
`TestTheHardeningStatusTableMatchesTheTree`: the fuzz targets and their time, the analysers and
their pinned versions, the floor under the scenario count and its tiers, the authorization call
sites, the release-build checks `make dist` runs, the form of every `#nosec`, the versions of the
libraries named, that Dependabot and CI are absent, and that every test cited here exists.

| Area | Where it stands |
|---|---|
| Automated tests | Go tests under `-race` over both storage engines: SQLite always, Postgres when `HDTP_TEST_POSTGRES_DSN` is set, which the pre-push hook always does by starting a container ([`githooks/pre-push`](githooks/pre-push)). The limits sidecar's cargo tests (`make limitd-check`), the portal's page scripts and pure modules under `node --test` (`make test-js`), and the scenario harness ([`docs/harness-design.md`](docs/harness-design.md)): a hermetic tier with no Docker (`make harness`) and more than 25 live scenarios in three nested tiers, fabric, PR and nightly (`harness list` prints the registry) that stand up real nodes, real mTLS, real NAT and a real Chrome, opt-in on push with `HDTP_PREPUSH_LIVE=1` or `full`. There is no CI: `.github/` holds no workflow. The pre-push hook runs `make check`, `make analyze`, `make sqlc-check`, `make fuzz`, `make harness` and `make scale`, and refuses the push when one fails; hooks are never bypassed ([`CONTRIBUTING.md`](CONTRIBUTING.md)) |
| Fuzzing | Four targets, 30 s each under `-fuzz` in `make fuzz`, on every push: `FuzzVCardParse` (a peer's card), `FuzzSealedEnvelope` (the whole open of a sealed call, from arbitrary bytes to the refusal code), `FuzzInviteOffer` (the offer document an owner is about to pin an identity out of) and `FuzzRedact` (what an upstream server's error may put in the audit trail). `TestEveryFuzzTargetRunsUnderMakeFuzz` fails when a target exists that `make fuzz` does not run. Nothing runs them for longer: there is no continuous fuzzing |
| Static analysis | `govulncheck` v1.1.4, `staticcheck` 2025.1.1, `gosec` v2.22.9 and `deadcode` v0.49.0, each run as `go run <module>@<version>` from the one list in the [`Makefile`](Makefile) (`analyze`), on every push. govulncheck also scans upstream frp on its own, since the tree carries a patched copy of it (`scripts/frp-patch.sh`). staticcheck runs its defaults less ST1005 ([`staticcheck.conf`](staticcheck.conf) says why). gosec runs with G101, G104 and G304 excluded and `harness`, `third_party` and `.claude` skipped (the Makefile says why), and every `#nosec` in the tree names the rule it waives and the reason on the same line; most waive G402 on an `InsecureSkipVerify` whose connection is then pinned to a key below it rather than validated against a chain (HDTP §2). deadcode is held to the Reachability table of [`docs/conformance.md`](docs/conformance.md) (`TestDeadcodeFindsOnlyWhatTheTableExcuses`) |
| Dependencies | Bumped by hand and gated by the hooks; no Dependabot (`.github/dependabot.yml` does not exist) and no GitHub Actions (`.github/workflows` does not exist): every gate runs on the machine that pushes, and `githooks/pre-push` says why. hdtp-identity is required by version (`go.mod`: v0.8.0) through the public module proxy and checksum database, never by path. The one vendored dependency is frp v0.71.0 plus one patch (`third_party/frp`), held to upstream byte for byte by `make frp-check` in `make check`. `THIRD_PARTY_NOTICES` is held to `go.sum`, `Cargo.lock` and `package-lock.json` by hash (`make notices-check`, in `make check`) |
| Owner surface authentication | WebAuthn passkeys (`go-webauthn` v0.18.1; `internal/internalui/auth/passkeys.go`). An owner session on every bind, loopback included (`TestLoopbackStillDemandsALoginAndHostIsNotTrusted`); the only portal state no session guards is the setup wizard, which the node serves while it holds zero passkeys, from loopback or with the one-time setup token (`TestWizardLoopbackZeroPasskeys`, `TestWizardNonLoopbackNeedsToken`, `TestWizardGoneOncePasskeyExists`), and otherwise only to a recovery token. Losing every passkey takes host shell access to recover from: `hdtp-gateway passkey reset-wizard`, over the admin unix socket, mints that recovery token, good for 24 hours (`internal/internalui/server.go`); there is no online recovery. The owner MCP takes a bearer token on every bind (`TestOwnerMCPRequiresATokenEvenOnLoopback`) and offers `list_passkeys` and `remove_passkey` only: a token cannot register a passkey (SPEC §3.1). A state-changing portal request carries the CSRF token, and `Sec-Fetch-Site` (else `Origin`) must say it came from this site (`TestEveryMutatingPortalRouteRefusesAForgedRequest`) |
| Release integrity | Cut locally by a maintainer from a tag ([`RELEASING.md`](RELEASING.md)): `make dist` builds four platforms with `CGO_ENABLED=0` and `-trimpath` and writes `SHA256SUMS`; `make sbom` writes a CycloneDX 1.6 SBOM. v0.1.2 ships the four binaries, `SHA256SUMS`, `sbom.cdx.json` and `THIRD_PARTY_NOTICES` (`gh release view v0.1.2`). No build provenance and no attestation: nothing binds a binary to a build anyone else saw. **Measured 2026-10-10: v0.1.2's linux/amd64 binary cannot be reproduced by RELEASING.md's check.** `go version -m` shows it stamped `vcs.modified=true`, module version `v0.1.2+dirty`: the checkout of the tag it was built from held an untracked or modified file. A clean clone of the tag, built as `make dist` builds (Go 1.26.9), gives a different checksum (`5bccb23e…`, `vcs.modified=false`); the same clone with one empty untracked file gives the published checksum (`3f942dc9…`) byte for byte, so the code is the tag's and only the stamp differs. A build from a `git archive` extraction or a linked worktree carries no VCS stamp at all and matches neither (`1c1018f0…`). Since #105, `make dist` enforces it: before building it runs `scripts/release-check.sh tree`, which refuses a tree `git status --porcelain` finds anything in (untracked files included) or a HEAD that is not the tag's commit, and after building `scripts/release-check.sh binaries`, which refuses a binary whose build info does not record `vcs.modified=false` and the tag's `vcs.revision`; `make sbom` runs the tree check too, and `make check` runs both against fixture repositories (`make release-check`, `scripts/release-check-test.sh`). v0.1.0 to v0.1.2 were built before it; the next release is the first built under it |
| Envelope construction | HPKE Base mode (RFC 9180) to the recipient's leaf key, `info` `HDTP-SEAL-v1`, the canonical protected header as AAD, and a detached signature by the sender's leaf over `protected ‖ enc ‖ ct`; two suites, fixed by the recipient's key type (P-256 with AES-128-GCM; X25519 with ChaCha20-Poly1305). The construction is hdtp-identity's (`hpke.go` and `envelope.go` of the Go port this node links), not this repository's; this node's use of it is `internal/public/decide.go` and `sealed.go`, and HDTP Appendix B's vectors are reproduced by the Rust core, its Wasm build and the Go port. **No independent cryptographic review.** [`docs/crypto-review-brief.md`](docs/crypto-review-brief.md) states the construction and the eight questions (Q1 to Q8) we want a reviewer to answer, the key reuse and the plain-concatenation signature input first |
| Key separation | None, by decision: one leaf keypair is the TLS server key (the chain served per SNI, `internal/public/listener.go`), the TLS client certificate (`internal/node/outbound.go`), the HPKE recipient key and the envelope signing key (SPEC §2.5, §13.2). HDTP §13.5 bounds it: that key signs four structures, a TLS handshake, a certificate signing request, a card and an envelope, each distinguishable by its first bytes, and nothing else. A reviewer should expect to raise it (the brief's Q1 and Q6); the envelope's `kid` is the seam for a separate sealing key |
| Interoperability | Two implementations, both this project's: this node and BatonDeck, the hosted platform, sharing hdtp-identity 0.8.0 (the Go port here, the Wasm build of the same crate there, pinned by hash), whose own two ports are held to each other case by case (`hdtp-identity/js/parity.mjs`). BatonDeck's Go conformance battery (`batondeck/gateway/conformance`, a private repository) drives a node in the nightly tier (S19) and the hosted platform from its `make conformance`. hdtp-identity's intrusion battery runs offline over both ports (157 scenarios at 0.8.0: 151 blocked, 6 residual by decision, 0 reproduce; `node js/intrude.mjs`, 2026-10-10) and its 28 live scenarios against a node (S18) and against the hosted platform (`js/live-scenarios.json`, one list both drivers read). No implementation from outside the project exists, and SPEC §14.1's suite runnable against any node from outside does not exist either, so "conformant" means "agrees with ourselves" |
| Identity confusion | A peer's name is capped at 64 runes (`contacts.MaxDisplayName`), stripped of control and format characters but the joiners, so no bidi override repaints the row (`identity.StripDisplayName`), and never changed by a card refresh once pinned (`TestACardRefreshCannotRenameAPinnedContact`). For collision, names are compared by PRECIS Nickname (RFC 8266) plus a cross-script look-alike fold, Cyrillic and Greek to Latin (`internal/internalui/labels.go`), held equal to BatonDeck's copy through `testdata/contact_labels.json` (`TestTheLookAlikeTableIsTheFixtures`, `TestContactLabelsAnswerTheSharedCases`); a peer-chosen name that collides is shown with its fingerprint. The durable answer is the owner's petname, which no peer-facing surface can set (`TestNoPeerFacingSurfaceCanSetAPetname`). Within-Latin look-alikes (`l`/`I`/`1`, `rn`/`m`) are a known gap, by decision |
| Rate limiting | The call budgets of HDTP §12 are decided outside the node process, by the limits sidecar `hdtp-limitd` (`cmd/hdtp-limitd`, Rust, hdtp-identity's `hdtp-limits` crate; its numbers [`deploy/limitd/limits.json`](deploy/limitd/limits.json)), asked over a unix socket (SPEC §5.7); while it is down every budgeted call is refused `unavailable` rather than served unmetered (`TestEveryBudgetIsRefusedUnavailableWhileTheSidecarIsDown`), and the guest budget is spent on the real listener (`TestGuestRateLimitIsEnforcedOnTheRealListener`). Per-source flood control is not in the node at all: it is the proxy's, [`deploy/envoy/envoy.yaml`](deploy/envoy/envoy.yaml), a local rate limit per remote address (300 calls per 10 s on the MCP route, 60 per minute on invite landings and everything else), proven in the nightly tier (S23). Neither is DoS protection ([`docs/threat-model.md`](docs/threat-model.md), out of scope) |
| Authorization | One Cedar policy point, `internal/core/policy` (`cedar-go` v1.8.0), its policy text compiled into the binary: three call sites on the public surface (two build `tools/list`, in `internal/public/servers.go` and `sealed.go`; one gates every call after re-resolving the caller's tier, in `servers.go`) and `AllowOwnerManage` on the owner MCP. Tiers are exact surfaces, not ranks (`TestAllowExactTierAndPermission`, `TestBuiltinToolSurfacePerTier`); a blocked contact is served as a stranger, `tools/list` included (`TestBlockedCallerIsIndistinguishableFromAStranger`). In v1 a node has one owner role, `admin`, granted every account (`internal/identity/membership.go`); the account-isolation tests (the threat model's boundary 4) hold what a narrower grant would rely on |
| Audit chain | Every row is bound to the one before by SHA-256 (`internal/core/audit`); `hdtp-gateway audit verify` re-walks the chain; archiving writes, reads back and verifies before it deletes, so pruning keeps the chain verifiable from genesis (`TestAuditTamperedExportDetected`, `TestAuditArchivePrunesAndKeepsTheChainVerifiable`), and the fabric tier verifies the chains of real nodes (F4). A refusal by policy is audited as the call would have been (`internal/public/servers.go`). The chain detects an edit, a reorder or a removal after the fact; it is not anchored outside the host, so someone with the store who rewrites it whole from genesis is not detected (A6, out of scope) |
| Secrets at rest | Leaf private keys, integration credentials and secret settings are sealed with AES-256-GCM under one master key, bound by AAD to what they belong to: the column for keys, the integration for its credentials, one constant for settings (`internal/core/keyring.go`, the only write path for secrets at rest); the key comes from `HDTP_MASTER_KEY` or a 0600 file created in the data directory on first run, on the same machine as the store. Disk encryption is the operator's (A6, out of scope) |

[`docs/threat-model.md`](docs/threat-model.md) sets out the adversaries, assets and trust
boundaries and pairs each claim with the test that holds it; start there if you are reviewing. The
accepted trade-offs (no forward secrecy at the envelope layer, metadata visible to a carrier, a
lost root is a lost identity, one key for four jobs) are decisions recorded in SPEC §13.2 and
HDTP §13.5, not oversights. The rest of the table is what has not been done.
